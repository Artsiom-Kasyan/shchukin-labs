# Устройство API

Источник контракта — openapi.yaml в корне ветки. Схема Room описывает помещение, Slot содержит его идентификатор и две временные отметки. Booking расширяет Slot номером подтверждения. Руководство в docs/user.md использует те же поля, коды и примеры. Версия контракта — 1.0.0.

## Компоненты и порядок записи

Клиент читает каталог, запрашивает доступность, затем передаёт Slot обработчику POST /bookings. При реализации сервиса обработчик валидирует даты, ищет комнату и пытается записать бронь в транзакции. Идентификатор выдаётся при успешной записи. Аудитории с разными roomId имеют независимые расписания.

Сравнение выполняется по моментам времени после перевода в UTC. Интервалы полуоткрытые. Для слотов A и B конфликт возникает при A.start < B.end и B.start < A.end. Бронь 09:00–10:30 совместима с бронью 10:30–11:00. Слот 10:00–10:15 полностью попадает внутрь первого и должен получить 409.

Ответ availability отражает момент чтения. Два клиента могут одновременно увидеть свободное время. В постоянном хранилище проверка пересечения и вставка должны быть атомарны, например через ограничение исключения PostgreSQL по комнате и временному диапазону. Удаление по id освобождает слот.

## Локальный стенд

Prism читает файл спецификации и слушает localhost:4010. Сборка, база данных и переменные окружения для просмотра примеров не нужны. Режим mock позволяет проверить форму запросов и ответов; проверку гонок и сохранение состояния можно проводить на реализации сервиса. При смене порта укажите его параметром `-p` и измените адрес клиента.

Для проверки структуры установите openapi-spec-validator и выполните `python -m openapi_spec_validator openapi.yaml`. При изменении контракта обновите образцы запросов в руководстве и проверьте все ссылки на компоненты.
